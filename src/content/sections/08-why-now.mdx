### Store-centric excels at...

- **Predictability**: All state changes flow through explicit paths (actions, commits, events)
- **Debugging**: Easy to trace what changed and why (action logs, middleware, reducers)
- **Structure**: Enforces feature boundaries and unidirectional flow
- **Familiarity**: The dominant baseline in many ecosystems (Redux, MVI, MVVM, BLoC)

### Atomic / Graph-centric excels at...

- **Fine-grained derived state**: Small values compose into other values directly
- **Reduced wiring**: Dependencies can be discovered from reads instead of listed manually
- **Dynamic dependencies**: Dependencies can change based on runtime conditions
- **Scalability of derived state**: Adding a new derived value does not require modifying existing store wiring

### The real question isn't "which is better"

Both families need derived state. The question is whether the **dependency tracking for that derived state** should be:

1. **Manual** — the developer wires it (StateFlow `combine`, Zustand selectors)
2. **Explicit** — the developer declares a store-local pipeline (Verge `Derived`)
3. **Automatic** — the runtime discovers it (Jotai `get()`, Atoms `watch()`, Riverpod `ref.watch()`, TanStack Store `.state`, swift-state-graph ThreadLocal, Compose Snapshot)

Graph-based tracking reduces manual wiring cost. It can appear as the core model of atomic systems, as a signals-style store runtime, or as a supporting feature inside store-centric systems.

The trend is not a wholesale shift from store-centric to atomic/graph-centric. Rather, **derived state dependency management is becoming more explicit and more automated**, and each ecosystem is adopting that idea at a different layer.
